# 固定输入量化速度排查（2026-11-10）

结论：量化实际生效、权重和显存已缩小，但当前LMDeploy 0.11.1 PyTorch/eager W4A16执行路径没有在这两个固定输入上形成速度优势。长prefill的量化线性算子更慢；decode收益也未显现。不能把原因直接归结为“激活占比过大”。

保持第一/二阶段所有模型、冻结适配代码和结果不变。固定同两张/九张图及文本（701/2815输入token），实际input_ids/pixel_values哈希跨三模型完全一致。统一生成64token、greedy、batch1、eager、3072完整prefill、固定KV池、无prefix cache/Token裁剪。输出token内容可能因模型不同而变化，长度相同；不是导航质量测试。

完整原校验模式：FP16→AWQ→GPTQ和反向各一轮，每模型每输入每轮3次预热、4次测量，合计每档8次。独立关闭详细校验/执行hooks/记录的native对照每档4次。共72次计入统计的固定输入请求，均通过输入和计数复核。

表中为重复请求中位数。视觉/语言/模型区间来自CUDA events，可能包含GPU等待主机派发的空隙，不能当作纯内核累计耗时；TTFT是HTTP到首个输出token，包含模型前置开销。流式decode是首末输出token之间63个间隔的均值。实际后端每个测量请求执行1次prefill+64次decode，比64个返回token多一次前向，记录未丢弃；预热与独立profiler请求不混入统计。

1. **量化大矩阵路径效率不足。** 两算法部署都走相同的原生AWQ GEMM/Triton执行路径，参数值不同。长输入下语言prefill约404–405ms，FP16约332ms。真实第0层融合gate/up投影（2815行）单独验证：FP16约3.51–3.52ms，INT4约5.33–5.43ms；计算结果相对L2误差均小于0.01。该内核读取打包INT4权重，解包/缩放后与FP16激活做矩阵运算，减小权重存储并不等于四倍计算加速。单投影热缓存微测只解释实现线索，不替代全模型计时。

2. **未量化和服务前置开销占比较大。** 九图视觉编码仍约141–142ms。额外FP16归因请求中，前端图像处理约17ms，而前端prompt处理完成→工作进程开始prepare_inputs的间隔约894ms；两图该间隔约38ms。这个间隔覆盖跨进程传输/输入处理/调度等，尚未细分，不能直接全部命名为图像预处理或传输耗时。九图原始pixel_values为FP32约63.28MiB，与语言W4权重量化无关。

3. **详细校验有代价，但不足以解释全部问题。** 关闭它后，九图流式decode中位约FP16 22.59、AWQ 23.39、GPTQ 23.31ms/token，仍没有看到量化更快；语言prefill仍约336/408/409ms。此对照只做一轮，不能把小幅差异精确归为纯日志成本。

4. **“激活不压缩”是可能影响因素，尚未被证明为主因。** W4A16保持激活FP16，视觉、注意力、KV等也没有一并变INT4；但显存占比不能替代耗时占比。当前没有可用CUPTI内核活动跟踪，未测到能证明激活带宽饱和的证据。已测到的直接问题是当前INT4大矩阵路径较慢，以及公共前置开销。

原100条闭环中约8%的P95差异包含不同轨迹、输入和输出长度，不能当作固定工作量下的量化加速。本次诊断不覆盖原导航质量结果，也不修改原统计表。下一步应优先优化/核查W4A16内核与前端到工作进程间隔，再判断组合的实际性能收益；本次没有运行组合或改生产后端。

保留启动脚本误识别内部预热、离线导出步数假设不符两项诊断问题及原失败日志；修复没有重跑导航或改变权重。CUDA profiler初始化失败只影响内核活动归因，CUDA events和HTTP计时均有实际记录。原始日志、输入和模型仅保留本地。
